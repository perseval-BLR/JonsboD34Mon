# PC Monitor All (JONSBO): разбор

Программа: `C:\Program Files (x86)\PC\PC Monitor All\PC Monitor All.exe`, версия 1.0.0.0, .NET Framework 4.7.2, WinForms, 32-битный процесс.
Публичного исходного кода я не нашёл, поэтому разбирал декомпилированный код (ILSpy): около 5 400 строк, почти всё в одном файле `frmMain.cs`.

## Что программа делает на самом деле

1. Раз в секунду читает датчики через библиотеку **HWiNFO SDK** (`HWiNFO32.dll`).
2. Раз в 200 мс отправляет один 64-байтный HID-пакет на экран корпуса.
3. Всё остальное — окно с выпадающими списками, где выбирается, какой именно датчик показывать.

Экран видится в Windows как обычное HID-устройство, поэтому драйвер CyUSB не нужен:

| | |
|---|---|
| Устройство | `HID\VID_5131&PID_2007` (подключено, статус OK) |
| Частота отправки | каждые 200 мс (данные при этом обновляются раз в 1 с) |
| Команда при закрытии | `data[1] = 0x0F` (вероятно, «ПК выключается / погасить экран») |

### Протокол (то, что нужно для своей версии)

Буфер: `[ReportID][0x00][0x01][0x02][v0 … v32]`, остальное нули, всего 64 байта данных.

## Что я измерил (процесс работал 2,5 часа, свёрнут в трей)

| Показатель | Значение | Что это значит |

## Баги

### Критичные (нагрузка и утечки)

1. **Список процессов перечитывается 20 раз в секунду** (`showFrm`, стр. 584–601). Бесконечный цикл каждые 50 мс вызывает `Process.GetProcessesByName(...)` и проверяет, не запущена ли вторая копия программы. Созданные объекты `Process` не освобождаются. Скорее всего, именно отсюда и большая часть нагрузки на CPU, и рост дескрипторов. Правильная проверка второй копии — один `Mutex` при запуске.
2. **Опрос датчиков перебором** (`GetPCParam`, стр. 644–969). Для каждого датчика HWiNFO перебирает индексы 0…511 и для каждого вызывает `GetSensorValue` 8 раз (по разу на тип). Получается десятки тысяч вызовов неуправляемого кода в секунду, и в каждом копируется структура с несколькими строками по 128 символов. Кроме того, осталась отладочная печать `Console.WriteLine` на каждое найденное значение.
3. **`Application.DoEvents()` вызывается из фоновых потоков** (стр. 595, 640, 1831, 1868). Так делать нельзя: на фоновом потоке нет очереди сообщений, вызов в лучшем случае бесполезен, в худшем ломает работу окна.
4. **Утечка картинок** (`LoadBGImage`). Фон загружается через `Image.FromFile` (PNG по 2,4 МБ), старая картинка не освобождается. Когда экран переподключается, каждый раз утекает несколько мегабайт.
5. **Пока экран отключён**, раз в ~450 мс в UI-потоке пересоздаётся весь список USB-устройств (`Get_Devices`), и окно подтормаживает.

### Логика и данные

6. **Напряжение CPU всегда показывается с ошибкой.** Значение сначала округляется до целого (`Math.Round(value, 0)`, стр. 934), и 1,25 В превращается в 1. Потом в байт дробной части записывается `целое × 100` (стр. 1171) вместо дробной части. На экране получается мусор (обычно 1.00 V). У вас в config.ini как раз сохранено `Core 0 VID:1`.
7. **Температуры передаются без дробной части**: они тоже заранее округлены до целого, поэтому байты v1/v11 всегда 0.
8. **Частоты читаются без проверки `IsValid`** (стр. 775), в отличие от остальных показателей, поэтому могут попадать устаревшие значения.
9. **Сбой в списке «Помпа/СВО»** (стр. 1751): цикл идёт по одному списку (`WatarRPM.Count`), а элементы берёт из другого (`WatarRPM2`). Если датчик вентилятора пропадает, вылетает исключение, и список становится пустым.
10. **Выпадающие списки «прыгают»**: каждую секунду фоновый поток через `Invoke` переписывает текст всех 11 списков, даже если ничего не изменилось. Отсюда мерцание и сброс выбора.
11. **Общие списки без синхронизации**: фоновый поток меняет `ClsMain.CPUT` и другие списки, пока UI-поток их читает. Иногда это приводит к редким падениям, которые программа молча проглатывает.

### Настройки и интерфейс

12. **Автозапуск нельзя выключить.** При каждом запуске программа кладёт ярлык в папку «Автозагрузка», а галочка «Автозапуск» добавляет и удаляет только запись в реестре `HKLM\...\Run` (для этого нужны права администратора, без них ошибка молча проглатывается). Ярлык остаётся, и программа продолжает стартовать вместе с Windows.
13. **Пункт «Показ на экране» (CloseLED) ничего не делает**: значение переключается в меню, но никуда не отправляется и не сохраняется.
14. **Язык не сохраняется** в config.ini и после перезапуска сбрасывается.
15. **Меню выбора устройства перестраивается при каждой проверке**: списки сравниваются по ссылке (`List_HIDStr_OLD != List_HIDStr`), а не по содержимому, поэтому условие всегда истинно.
16. **Закрытие программы — это убийство собственного процесса** (`CloseAllProcesses`): `HWi.DeInit()` не вызывается, драйвер HWiNFO не выгружается.
17. **Первый запуск без нужных ключей в config.ini** заканчивается окном «GetParam is Err», и остальные настройки не загружаются: `Convert.ToInt16("ERR")` падает до того, как они прочитаны.
18. **Логи** пишутся в `Program Files\...\LOG\` с новым открытием файла на каждую строку. Старые логи никогда не удаляются.

### Мелочи
- Пакет шлётся 5 раз в секунду, хотя данные меняются раз в секунду. Достаточно 1 раза в секунду (часы на экране тоже идут по секундам).
- Внутри exe лежат 4 PNG по 2,4 МБ и ещё больше картинок в ресурсах окна. Отсюда большой размер файла и лишняя память.
- `ComputereMonitor.sys` (драйвер ядра) лежит в папке, но в коде не используется, и как служба в системе не установлен.

## Предлагаемая замена

| | Сейчас | Своя версия |
|---|---|---|
| Платформа | .NET Framework 4.7.2, 32-бит | .NET 8 (рантайм уже установлен), 64-бит |
| Датчики | HWiNFO SDK, перебор 512 × 8 вызовов на каждый датчик | Тот же `HWiNFO64.dll` из установленной папки, но индексы нужных датчиков находятся один раз при старте, дальше 10–12 точечных чтений в секунду |
| USB | CyUSB.dll | Стандартный Windows HID API (`hid.dll`), без сторонних библиотек |
| Окно | Тяжёлая форма с картинками, всегда в памяти | Значок в трее + компактное окно настроек, которое создаётся только при открытии |
| Отправка | 5 раз/с | 1 раз/с, повторная попытка при переподключении экрана |
| Ожидаемо | ~15 % ядра, 72 МБ, утечка | < 0,5 % ядра, ~20 МБ, без утечек |
